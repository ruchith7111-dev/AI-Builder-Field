# Contributing

Thanks for helping make this field notebook more useful. The goal is not to collect the most AI tips; it is to document lessons another developer can reproduce, question, or improve.

## What belongs here
- A reproducible experiment with setup, inputs, and observed results.
- A debugging note explaining the symptom, investigation, and evidence.
- A correction to a technical explanation or diagram.
- A useful counterexample showing when an approach does not work.
- A concise prompt pattern with a clear purpose and review criteria.

## Evidence rules

| Label | Meaning |
|---|---|
| **Observed** | Directly seen in a run, test, log, screenshot, or code inspection |
| **Tested** | Reproduced with a stated procedure and result |
| **Design note** | Planned or discussed architecture, not proof of implementation |
| **Hypothesis** | Plausible explanation that still needs testing |
| **Unknown** | Not yet checked |

Never turn a design note or hypothesis into a claim that something shipped or worked.

## Pull request checklist
- [ ] The title says what changed.
- [ ] Context is sufficient to understand the problem.
- [ ] Commands, versions, and assumptions are included where useful.
- [ ] Results are separated from interpretation.
- [ ] Secrets, personal data, and private project details are removed.
- [ ] Diagrams have useful alt text or an explanation.
- [ ] Video files are genuinely playable if described as videos.
- [ ] The change adds a reusable lesson rather than duplicate filler.

Write plainly. Prefer a small reproducible example over abstract advice. Admit when a result is unknown. Do not paste large AI-generated answers without checking them.
